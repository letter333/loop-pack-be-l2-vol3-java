# 대기열 스케줄러 배치 크기 산정 근거

## 1. 측정 환경

| 항목 | 값 |
|------|------|
| 인프라 | Docker (MySQL 8.0, Redis 7.0, Kafka 3.5.1) |
| 애플리케이션 | Spring Boot 3.4.4, Java 21, local 프로필 |
| HikariCP 커넥션 풀 | maximum-pool-size: 40, minimum-idle: 30 |
| Tomcat 스레드 | max: 200, min-spare: 10 |
| 테스트 도구 | K6 v1.7.1 |
| 테스트 데이터 | 상품 100만 건 (seedProductJob), 회원 100명 |

## 2. K6 부하 테스트 #1 — 대기열 없이 주문 API 직접 호출

### 테스트 시나리오

Ramp-up 방식으로 VU(가상 유저)를 점진적으로 증가:
- 10 VU (30초) → 30 VU (30초) → 50 VU (30초) → 100 VU (30초)
- 각 VU는 주문 생성 후 0.5~1.5초 대기
- VU별로 다른 유저, 반복마다 다른 상품 사용 (락 분산)

### 결과

| 지표 | 값 |
|------|------|
| 총 요청 | 5,749건 (4분 30초) |
| 성공 주문 | 5,564건 (96.8%) |
| 실패 주문 | 185건 (3.2%, 고부하 구간 타임아웃) |
| **성공 TPS** | **~19.7 req/s** |
| 평균 응답시간 | 994ms |
| P50 (중간값) | 243ms |
| P90 | 3.48s |
| P95 | 5.97s |
| 최대 응답시간 | 13.71s |

> SALE 상태 상품만 주문하도록 필터링하여 측정.
> 에러율 3.2%는 VU 100 구간의 고부하 시 DB 커넥션 타임아웃으로 발생.

### 응답시간 분석
- VU 10~30 구간: P50 ~200ms, 안정적 처리 (에러율 ~0%)
- VU 50 이상: P90이 3초 이상으로 증가 (DB 커넥션 경합 시작)
- VU 100: P95가 6초, 간헐적 타임아웃 발생

## 3. 배치 크기 산정

### 산정 공식

```
배치 크기 = 안정 TPS × 스케줄러 주기(초) × 안전 계수
```

### 파라미터

| 파라미터 | 값 | 근거 |
|----------|------|------|
| 측정 TPS | 19.7 | K6 측정 결과 (전체 성공 기준) |
| 안정 TPS | ~10 | 에러율 <1% 구간 (VU 10~30) 추정치 |
| 스케줄러 주기 | 10초 | fixedDelay 기반 |
| 안전 계수 | 0.6 | 프로덕션 환경의 GC, 다른 API 경합, 네트워크 등 고려 |

### 계산

```
보수적 기준 (안정 구간 ~10 TPS 기준):
  배치 크기 = 10 × 10 × 0.6 = 60명

적극적 기준 (전체 성공 TPS 19.7 기준):
  배치 크기 = 19.7 × 10 × 0.6 = 118명
```

### 결정: 배치 크기 = 50명

- 보수적(60)보다 약간 낮은 **50명**으로 결정
- 대기열 도입 목적이 "시스템 보호"이므로 여유를 두고 보수적으로 산정
- 토큰 TTL 5분 동안 최대 입장 인원: 50 × 30회 = 1,500명
- P90 응답시간이 3초 이내를 유지하는 수준으로 제한
- 프로덕션에서 부하 테스트 후 조정 가능 (설정값으로 외부화)

## 4. 설정값

```yaml
queue:
  admission:
    batch-size: 50        # 스케줄러 1회 입장 인원
    interval-ms: 10000    # 스케줄러 주기 (10초)
  token:
    ttl-minutes: 5        # 입장 토큰 유효시간
```

## 5. K6 부하 테스트 #2 — 대기열 적용 후

### 테스트 시나리오

테스트 #1과 동일한 Ramp-up (10→30→50→100 VU), 동일한 유저/상품.
대기열 활성화 상태에서 **전체 플로우** 실행: 대기열 진입 → 순번 Polling → 토큰 획득 → 주문.

### 결과 (interval-ms: 10000)

| 지표 | 값 |
|------|------|
| 총 주문 시도 | 886건 (4분 56초) |
| 성공 주문 | 774건 (87.4%) |
| 실패 주문 | 112건 (12.6%) |
| **주문 TPS** | **~2.6 req/s** |
| 주문 평균 응답시간 | 1.61s |
| 주문 P50 | 1.43s |
| 주문 P90 | 3.13s |
| 주문 P95 | 3.4s |
| 전체 플로우 P50 | 10.79s |
| 전체 플로우 P95 | 22.11s |

> 에러율 12.6%는 Polling 타임아웃(대기열에서 토큰을 못 받은 경우)과 SALE 아닌 상품 주문 포함.

### 개선: 스케줄러 주기 10초 → 5초로 단축

테스트 #2 결과에서 전체 플로우 P50이 10.79s로 대기 시간이 길고, 주문 TPS가 2.6으로 과도하게 제한되는 문제가 있었다.
주문 P95(3.4s)는 안정적이었으므로, 스케줄러 주기를 단축하여 입장 빈도를 높이는 것이 가능하다고 판단했다.

### 결과 (interval-ms: 5000)

| 지표 | 값 |
|------|------|
| 총 주문 시도 | 1,141건 (5분 13초) |
| 성공 주문 | 998건 (87.5%) |
| 실패 주문 | 143건 (12.5%) |
| **주문 TPS** | **~3.2 req/s** |
| 주문 평균 응답시간 | 2.0s |
| 주문 P50 | 1.29s |
| 주문 P90 | 3.03s |
| 주문 P95 | 3.49s |
| 전체 플로우 P50 | 6.57s |
| 전체 플로우 P95 | 23.57s |

### 스케줄러 주기 변경 효과

| 지표 | 10초 주기 | 5초 주기 | 변화 |
|------|----------|---------|------|
| 성공 주문 | 774 | **998** | **+29%** |
| 주문 TPS | 2.6 | **3.2** | **+23%** |
| 전체 플로우 P50 | 10.79s | **6.57s** | **39% 개선** |
| 주문 P95 | 3.4s | 3.49s | 유사 (안정 유지) |
| 에러율 | 12.6% | 12.5% | 유사 |

스케줄러 주기 5초가 처리량과 대기 시간 면에서 더 효율적이므로 `interval-ms: 5000`으로 최종 결정.

## 6. Before / After 최종 비교

| 지표 | #1 (대기열 없음) | #2 (대기열, 5초 주기) | 변화 |
|------|-----------------|---------------------|------|
| 주문 성공 건수 | 5,564 | 998 | 처리량 제한 (의도적) |
| 주문 에러율 | 3.2% | 12.5% | Polling 타임아웃 포함 |
| 주문 P95 응답시간 | 5.97s | **3.49s** | **42% 개선** |
| 주문 P90 응답시간 | 3.48s | **3.03s** | **13% 개선** |
| 최대 응답시간 | 13.71s | - | 고부하 타임아웃 제거 |

### 분석

1. **시스템 보호 효과 확인**: 대기열이 동시 주문 수를 제한하여 DB 부하를 분산. P95 응답시간이 5.97s → 3.49s로 개선.
2. **처리량 트레이드오프**: 전체 주문 건수는 5,564 → 998로 감소. 대기 시간이 발생하는 대신 주문 API의 안정성이 향상.
3. **대기 시간 허용 범위**: 전체 플로우 P50이 6.57s. 유저는 평균 ~6초 대기 후 주문 가능. 대기 화면(순번 조회 API)으로 UX 보완 가능.
4. **에러율 12.5%의 원인**: 대부분 Polling 타임아웃(스케줄러가 처리하기 전에 K6 최대 시도 횟수 초과). 실제 운영에서는 Polling 주기와 최대 대기 시간을 조정하여 개선 가능.

## 7. 추가 개선 시도

### 배치 크기 70 실험 결과 (실패)

배치 크기를 50 → 70으로 늘려 테스트한 결과:

| 지표 | batch=50 | batch=70 | 변화 |
|------|---------|---------|------|
| 에러율 | 12.5% | **20.6%** | 악화 |
| 주문 P95 | 3.49s | **5.05s** | 악화 |
| 성공 주문 | 998 | 781 | 감소 |

배치 크기를 늘리면 동시 주문이 증가하여 DB 커넥션 경합이 심화된다. **batch-size=50이 최적값**임을 확인하고 원복.

### Polling 주기 동적 조절 (적용)

순번 조회 응답에 `suggestedPollIntervalMs` 필드를 추가하여 클라이언트가 순번에 따라 Polling 주기를 조절하도록 구현.

| 순번 구간 | suggestedPollIntervalMs | 이유 |
|----------|------------------------|------|
| ≤ batchSize (50) | 1000ms (1초) | 다음 배치에서 입장 가능, 빠르게 감지 |
| ≤ batchSize × 3 (150) | 2000ms (2초) | 2~3 배치 후 입장, 적당한 빈도 |
| > batchSize × 3 | 5000ms (5초) | 대기 시간이 길어 빈번한 Polling 불필요 |

이를 통해 대기열 앞쪽 유저는 토큰 발급을 빠르게 감지하고, 뒤쪽 유저는 불필요한 Polling을 줄여 서버 부하를 낮춘다.

## 8. 최종 설정값

```yaml
queue:
  admission:
    batch-size: 50        # 70 시도 후 50이 최적임을 확인
    interval-ms: 5000     # 10초 → 5초로 조정 (K6 테스트 기반)
  token:
    ttl-minutes: 5
```
